## 已定

### ADR-001　规则核心与运行时解耦　【2026-09-20 修订理由，结论不变】
**日期**：2026-09-20
**背景（原）**：用户希望为"下个版本可能的 Lua 支持"提前准备，我初次检索认为 Lua 无证据。
**背景（修订）**：二次核查表明该判断过重 —— 官方已预告「可挂载客户端脚本的控件」，
多位创作者的创体服视频提及 Lua（详见 docs/01-research.md）。**原判断被推翻，但本决策结论不变，
且理由更强了。**
**决定**：`src/core/` 保持零依赖纯逻辑；所有运行时相关产物走 `src/adapters/`。
**修订后的理由**：现在同时存在两条可能的落地路径（节点图 / 客户端脚本），而且**两条都要用**
（服务端走节点图，客户端走脚本）。核心解耦从"防御性设计"变成"必需品"：
纯函数移植到 Lua 近乎机械翻译，移植到节点图才是苦活，两边共用同一份可信参考实现。
**代价**：核心里不能用任何 Node 专有 API（已由 `tools/port-check.mjs` 自动检查）。

### ADR-002　零依赖
**日期**：2026-09-20
**决定**：核心与测试不引入任何 npm 包。
**理由**：① 目标运行时（节点图）本身不支持 npm，依赖越少移植越省事；② 单人项目，`npm install` 失败是纯粹的时间损耗；③ 移植到节点图时，每个依赖都是要手工重写的债。
**例外**：`gsts/` 子工程接 genshin-ts 时会有依赖，但那是适配器层，不污染核心。

### ADR-003　确定性随机
**日期**：2026-09-20
**决定**：洗牌用可播种的 xorshift32（`makeRng(seed)`），不用 `Math.random()`。
**理由**：同一 seed 下本地模拟与局内表现完全一致，bug 可复现。测试里已验证。

### ADR-004　服务端权威
**日期**：2026-09-20
**决定**：词典校验、计分、回合推进全部在服务端节点图；客户端只提交意图、只做表现。
**理由**：客户端可伪造消息。词典校验放客户端 = 玩家可以拼任意字符串得分。

### ADR-005　脚本能力的对待方式
**日期**：2026-09-20
**背景**：7.1（9-23 上线）官方预告「界面编辑新增一类可挂载客户端脚本的控件」，
创作者视频提及 Lua，但官方完整 API 文档尚未放出（指南更新日志最新仍为 7.0）。
**决定**：
1. **按"客户端脚本即将可用"准备，但不把任何具体 API 写进方案**，等实测。
2. **不预先创建 `src/adapters/lua/`** —— 没有 API 文档时写的适配器必然要重写。
3. 先做准备工作中**不依赖 API 的那部分**：核心可移植性（已完成）、
   Lua 基础（table / 闭包 / 模块 / 错误处理）、服务端-客户端职责切分（已在 ADR-004 定好）。
4. **拿到正式 API 后再大量用 AI 生成代码** —— 否则会生成看似合理但不存在的接口。
**理由**："支持脚本"不等于"具备完整能力"。服务端逻辑、联网接口、文件访问是否开放全是未知数，
现在押注等于赌博。而核心解耦已经让等待的成本接近零。

### ADR-006　客户端脚本不承担裁决
**日期**：2026-09-20
**决定**：即使客户端脚本能力很强，词典校验、计分、回合推进、牌堆一律留在服务端节点图。
客户端脚本只做表现层：高亮、拖拽预览、动画、补间。
**理由**：客户端可被伪造。词典校验放客户端 = 玩家可以拼任意字符串得分。
这是 ADR-004 在新信息下的再确认 —— **新能力开在客户端，恰好开在不能放裁决的那一侧**。
**副作用（正面）**：分桶词典的工作完全不受影响，它本来就注定在服务端。
